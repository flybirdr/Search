# 超大文件并行分块搜索方案

> 适用场景：单个文件几百 MB 到几 GB（日志、dump、单行 JSON、数据库导出）。
> 目标：**在内存不随文件变大的前提下，把单文件搜索从「单核吞吐」提升到「多核吞吐」**，
> 且结果与串行搜索逐字节一致（行号、列号、预览、命中数）。

## 1. 问题：为什么已有的三条路径都不够

| 现有路径 | 并行维度 | 单文件吞吐 | 内存 |
| --- | --- | --- | --- |
| 整块读入（`< streamThresholdKB`） | 无 | 单核 | ≈ 文件大小 |
| 串行流式（`stream.ts`） | 无 | 单核 + 一条顺序读流 | 恒定（2 × 块） |
| 多文件 worker 池（`workerPool.ts`） | **文件之间** | 仍然单核——一个文件只由一个 worker 处理 | W × 单文件缓冲 |

在多文件工作区里，池化让 N 个文件同时跑，吞吐随核数上升。但只要**某一份文件特别大**，
它就变成一条长尾：池子里 15 个 worker 早已空闲，最后那个 worker 还在单核啃那份 2GB 日志。
整读路径更糟——2GB 直接顶爆内存；流式路径正确但只有一个核在动。

本方案补的正是这个缺口：**把「一个文件」变成「多块活」，塞进同一条工作队列**。

## 2. 并发与分块策略对比

| 方案 | 并行维度 | 内存 | 顺序读友好 | 实现复杂度 | 在本项目的可行性 |
| --- | --- | --- | --- | --- | --- |
| A. 单线程顺序读 + 单核匹配（现状） | 1 | 2 × 块 | 最好 | 已有 | 基线 |
| **B. 按行对齐切块，多 worker 各扫一块（本方案）** | **核数** | **W × 块** | 好（每块一次顺序读） | 中 | ✅ wasm 单线程，天然要一实例/线程 |
| C. 读线程 + 匹配线程流水线 | 2 | 队列深度 × 块 | 最好 | 中高 | ⚠️ 匹配仍是单核，只在 I/O 与 CPU 等量时才有效 |
| D. mmap + 多线程指针跳跃（ripgrep 风格） | 核数 | 虚拟内存 | 差（随机换页） | 高 | ❌ wasm32 无 mmap；32 位地址空间也放不下 GB 级映射 |
| E. 异步 I/O / 协程并发读 | I/O 并发 | 队列深度 × 块 | 差（并发随机读） | 低 | ❌ worker 内异步 fs 走宿主共享的 libuv 池（默认 4 线程），实测比同步慢 3 倍（0.1.50~0.1.54 回归） |
| F. 共享内存 + 原子游标（线程内协作） | 核数 | 共享 | 好 | 高 | ❌ wasm 未开 threads；SharedArrayBuffer 需要额外构建标志 |

**为什么选 B**：

1. **瓶颈在 CPU**。日志类文件通常在页缓存里（或顺序读的带宽远大于匹配速度），真正的成本是
   内核逐字节扫描。既然匹配是 CPU 密集，唯一有效的并行维度就是「多个核同时扫不同字节」。
2. **wasm 内核是单线程的**。并行 = 多个 wasm 实例 = 多个 worker 线程，这正好与本项目已有的
   线程池同构（一个 worker 一份实例，各自 `putBytes` 到自己的线性内存，零共享、零锁）。
3. **按行对齐的块**让正确性问题几乎消失：块起点是行首，列号/预览/行号都可以局部算出，
   单行内的模式**根本不需要重叠**。
4. 块本身就是「够大的一坨活」，可以直接塞进已有的 `work-stealing` 队列，与普通文件共享
   负载均衡、取消广播、worker 常驻等全部机制。

不选 D 的现实原因：wasm32 的地址空间上限 4GB，mmap 一个 8GB 文件连地址都装不下；而且
mmap 的随机换页在冷缓存 / 机械盘上会把顺序读优势全部吐回去。

## 3. 整体架构

```
                 ┌──────────────── 宿主（TS, 扩展线程）────────────────┐
真实文件 ──stat──► │ worker A: 发现 size > chunkAbove                     │
（超大）          │   ├─ 探测编码（BOM/NUL）→ 非 UTF-8 就地退回串行       │
                 │   ├─ chooseChunkSize()   → 块大小 / 并发度            │
                 │   └─ planChunkRanges()   → [{start,end,readEnd}, …]   │
                 │                        │                              │
                 │   result: {kind:'plan', ranges}                        │
                 │                        ▼                              │
                 │   applyBatch(): 把 ranges 变成 chunk 工作项           │
                 │   queue.unshift(...)   ← 插到队头，长尾优先摊开        │
                 └────────────────────────┬──────────────────────────────┘
                                          │ work-stealing（一次一块）
        ┌──────────────┬──────────────────┼──────────────────┬──────────────┐
        ▼              ▼                  ▼                  ▼              ▼
   worker 1       worker 2           worker 3           worker 4   …  worker W
   readRange()    readRange()        readRange()        readRange()
   putBytes()     putBytes()         putBytes()         putBytes()
   find_all()     find_all()         find_all()         find_all()
        │              │                  │                  │
        └──────────────┴─────── chunk 结果（块内行号）────────┘
                                          │
                 ┌────────────────────────▼──────────────────────────────┐
                 │ ChunkFiles 装配器（按 fileIndex 攒块）                 │
                 │ mergeChunkParts(): 行号 + 基准行号、上限截断           │
                 │ → 一条普通结果组 → 面板（按路径插入排序）              │
                 │ → 结果缓存 put（下次搜索直接回放，不再分块）           │
                 └───────────────────────────────────────────────────────┘
```

要点：

- **不需要宿主预扫全部文件**。体积是 worker 自己 `stat` 出来的（它本来就要 stat），发现超阈值
  才回报 plan，零额外 I/O。
- **分块与普通文件共用一条队列**，所以一份大文件的块可以和别的文件交错执行，收尾时不会空转。
- **块是「一次只派一块」**（`assign` 里对 chunk 项 take=1）：块够大，一次抓一把会让
  work-stealing 退化成静态分片。
- **补块场**：worker 要等自己的活干完、队列已空才腾出手回报 plan，那一刻别的 worker 大多
  已经收工——分块会掉到单线程上。所以主场结束后，宿主把「还没跑到的块」收起来单开一场，
  交给全部 worker（此时池子是热的，启动成本毫秒级）。实测 32 块 / 8 线程：不给补块场是
  321ms（等于串行），给了是 76ms。
- **装配只在文件的所有块到齐时发生**，所以结果组内部的行号天然升序，面板的「按路径插入」
  逻辑不受影响。
- 这条路径**不覆盖**：非 UTF-8（UTF-16 BOM / GBK）、二进制、单行超长文件——它们由 worker
  就地退回串行流式（`stream.ts`），用户看不到差别，只是这份文件不快。

## 4. 块大小与并发度：怎么算、为什么这么算

```
workers          = 池子线程数（parallelWorkers，自动档 = min(文件数, 16)）
memoryPerWorker  = chunkMemoryMB（默认 32MB）
overlap          = 模式可能跨行 ? 64KB : 0
minChunk         = 1MB
maxChunk         = 64MB

optimal       = √(size × 0.12ms × 330MB/s)     成本最优块大小（见下）
balanceLimit  = ceil(size / (workers × 4))      每 worker 至少 4 块
memoryCap     = max(minChunk, memoryPerWorker − overlap)
desired       = min(optimal, balanceLimit)
chunkSize     = clamp(desired, minChunk, min(maxChunk, memoryCap))
chunkCount    = ceil(size / chunkSize)
concurrency   = min(workers, chunkCount)
```

### 3.1 块大小：成本最优值是 √S，不是线性

单文件总耗时拆成三项（S 字节、c = 每块固定开销、v = 单核吞吐、b = 一批几块）：

```
T(C) = S/(W·η·v)  +  (S/C)·c  +  C·b/v
       理想并行          每块开销      尾延迟
```

第一项与 C 无关，对后两项求导置零：`-S·c/C² + b/v = 0` →

```
C* = √(S · c · v / b)      实际取值 √(S × 0.12 × 337920)，b=1
```

块长一律**向上对齐到 4KB**（内存页 / 扇区），避免每次 `readSync` 落在扇区中间产生读放大；起点仍按行首对齐，所以对齐的是长度不是偏移。

**块大小随文件大小按平方根增长**：文件大 4 倍，块只该大 2 倍。旧规则 `S/(4W)` 是线性的，
对 1GB 以上切得过粗：

| 文件 | 旧规则 | 成本最优 | 尾延迟（旧 → 新） |
| --- | --- | --- | --- |
| 100 MB | 3.1 MB | 1.97 MB | 9ms → 6ms |
| 1 GB | 16 MB（8 线程 32MB 内存档会截断） | 6.3 MB | 48ms → 19ms |
| 8 GB | 128 MB（被 64MB 上限截断） | 17.8 MB | 194ms → 54ms |

块变小会让每块开销变多（`S/C` 次），所以不是越小越好——求导求的就是这两项的交点。
`balanceLimit` 仍作为**下界**保留：小文件（< 4W MB）的成本最优值低于 1MB，会被
`S/(4W)` 和 1MB 下限顶住，块比较细，尾延迟天然短。

### 3.2 一次派多少：按字节预算，不按个数

`decideStealCount()`（`parallelism.ts`）：

```
remaining = (队列 + 已派未回) × 已 stat 文件的平均大小
budget    = min(remaining × 0.25 / workers, 8MB)
block 批   = min(want, 4, round(budget / 块大小))
file  批   = min(want, 512, budget / 平均文件大小)
```

- **0.25** 的意思是每轮派出「一个 worker 还应承担的工作量的四分之一」，一场下来有 4 次
  被重新均衡的机会。
- **按字节而不是按个数**：`asic_reg` 那批 6.5MB 头文件路径连续，按个数会一次领走几百个
  （GB 级），那个 worker 单干好几秒，其它线程只能扫小文件。按字节预算它只会拿到 40~50 个。
- 密集期预算顶到 8MB → 小文件一批几百个（往返开销摊薄）；尾声预算掉到几十 KB → 一次 1 个
  （最细粒度收尾）。**批量大小自己随剩余工作量缩放，不需要单独的配置项。**
- 块条目上限 4 块：预承诺太多会把 work-stealing 退化成静态分片。

| 文件大小 | optimal | balanceLimit | 结果 chunkSize | 块数（W=8） | 并发 |
| --- | --- | --- | --- | --- | --- |
| 4 MB | 0.39 MB | 0.125 MB | 1 MB（下限） | 4 | 4 |
| 20 MB | 0.88 MB | 0.63 MB | 1 MB（下限） | 20 | 8 |
| 100 MB | 1.97 MB | 3.1 MB | 1.97 MB | 51 | 8 |
| 1 GB | 6.3 MB | 32 MB | 6.3 MB | 163 | 8 |
| 8 GB | 17.8 MB | 256 MB | 17.8 MB | 461 | 8 |

**并发度**只能是 `min(workers, 块数)`：块是不可再分的单位，8 个 worker 抢 4 块不会有额外收益。

### 4.1 值不值得拆：收益判据（0.1.77 起）

体积门槛只说「这个文件够大，看一眼」，真正拆不拆由 `shouldChunk()` 逐文件算：

```
T1 = size / 330MB/s                              串行预估（实测单核字节路径吞吐）
T2 = T1 / (有效并发 × 0.6) + 1.5ms + N × 0.12ms   分块预估
拆当且仅当  N ≥ 2  且  T1 − T2 > max(4ms, 15% × T1)
```

- `1.5ms` 是每文件一次的固定成本（探编码 + plan 往返 + 装配），`0.12ms` 是每块一次的。
- `0.6` 是并行效率：8 线程实测 4.75x → 0.59。异构核（P+E）上 16 线程也到不了 12x，
  E-core 单线程吞吐只有 P-core 的 ~55%，16 线程的现实上限大约 8~9x。
- 阈值取 `max(4ms, 15%)`：4ms 是感知下限，15% 让判据随机器快慢自动缩放。

| 文件 | 串行 T1 | 块数 / 并发 | 分块 T2 | 净收益 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 2 MB | 6 ms | 2 / 2 | 6.9 ms | −0.7 ms | 不拆（拆了更慢） |
| 3 MB | 9 ms | 3 / 3 | 7.0 ms | 2.3 ms | 不拆（过不了 4ms） |
| 4 MB | 12 ms | 4 / 4 | 7.2 ms | 5.2 ms | 拆 |
| 10 MB | 31 ms | 10 / 10 | 7.9 ms | 23 ms | 拆 |
| 64 MB | 198 ms | 64 / 16 | 30 ms | 168 ms | 拆 |

### 4.2 池子忙不忙：拥挤闸门（按字节算，不按文件个数）

```
avgBytes      = 已 stat 文件的平均大小（只采样 ≤ 1MB 的「典型大小」）
perWorker     = (queue + inFlight) × avgBytes / workers      单个 worker 还剩多少字节
合并成单块  ⇔  size ≤ chunkCrowdMB（默认 2）  且  size < perWorker × 0.25
```

池子还不缺活干时，拆开这个文件只是把别的活顺延，总时长不变，却多付装配与消息
往返。所以只在它占比可观时才并行。

**判据必须用字节**：kernel 树 8 万个文件里混着 300 个 6.5MB 的自动生成头文件，
按个数算只占 0.4%（永远不值得拆），按字节算是一半以上。而且它们路径连续，会被
同一个 worker 一口气领走 —— 队列长度还是几万，但队列里全是几毫秒的小文件，那个
worker 却要单干好几秒。按个数判断恰好会在这种最需要拆的场景里判「不拆」。

「待办」必须是 `queue + inFlight`：work-stealing 一次能给单个 worker 派上百个文件，
几百个文件的目录会在 1ms 内把 queue 清空，活其实都还在 worker 手里。

平均值的采样要排除 > 1MB 的文件：否则被判断的那个 6.5MB 文件会自己抬高分母，
把「该拆」判成「不该拆」。

### 4.3 plan 必须立即上报

`plan` 是控制消息而不是普通结果，worker 收到就要 `flushPending`：宿主拿到区间才能
把块派回队列，块越早进队列，其它 worker 越可能顺手领走。压到批末（等本批 24 个
文件都处理完）会让大文件白等一整个批次——长尾就是这么长出来的，而且宿主收到 plan
时队列往往已经见底，拥挤判据也会失真。

**机械盘 / 网络盘**建议把 `parallelWorkers` 调到 2~4：并发读会让磁头来回寻道，顺序读优势被吃掉，
此时瓶颈从 CPU 变成 seek，加线程反而更慢。

## 5. 边界情况与应对

| 边界 | 处理 | 代价 |
| --- | --- | --- |
| **块起点切在字符中间** | 块起点一律对齐到**行首**（`\n` 之后；`\r\n` 跳过两字节；孤立 `\r` 之后）。行首必然也是 UTF-8 字符边界，所以起点永远安全。 | 无 |
| **块尾切在多字节字符中间** | 读区间终点按 `end + overlap` 硬截，可能切在字符中间。`trimIncompleteUtf8Tail()` 截掉末尾不完整序列（≤3 字节），否则 `utf8_valid` 会误判整块非法并让整份文件退回串行。截掉的字节本来就在重叠区，由下一块完整覆盖。 | 无 |
| **文件末尾不足一个分块** | 最后一块 `end = size`、`readEnd = size`，重叠按文件末尾截断。行数按实际行首数统计。 | 无 |
| **末尾没有换行** | `countStartsBefore` 只数 `< end` 的行首，末行不会被算成两行（与编辑器一致）。 | 无 |
| **模式被块边界截断** | 分两种情况：①**单行内的模式**（普通 / 扩展的 `\t` / 正则不含换行构造）→ `overlap = 0`，边界是行首，匹配不可能跨界，**零漏报**；②**可能跨行的模式**（`dotAll` 的 `.`、`\n`、`\s`、`\x0a`）→ `overlap = 64KB`，匹配起点在 `[start, end)` 内即归属本块，重叠区保证长度 ≤ 64KB 的跨行匹配完整可见。超过 64KB 的跨行匹配跨块可能漏——与串行流式路径的固有限制完全一致，不额外变差。 | 每块多读 64KB |
| **重复命中** | 归属规则是「匹配**起点**落在 `[start, end)` 才归本块」。重叠区里被重复扫到的匹配会因为起点 ≥ `end` 被丢弃。 | 无 |
| **整块没有换行（单行几百 MB）** | 向后找 `MAX_ALIGN_LOOKAHEAD`（8MB）仍无换行 → `planChunkRanges` 返回 `fallback: 'long-line'`，worker 就地退回串行流式（它本来就会硬切 + 多字节对齐）。硬切会切坏列号，绝不硬切。 | 这份文件不快 |
| **非 UTF-8 / 二进制** | worker 的 plan 阶段先探前 8KB：UTF-16 BOM / NUL → 直接退回串行（由 `stream.ts` 负责 BOM 转码与二进制判定）。极少数「前 8KB 是 UTF-8、后面混了非法序列」的文件，会在某一块的 `utf8_valid` 上暴露：回报 `chunkUnsupported`，宿主丢掉半份装配、把整份文件改回串行重扫。 | 该文件多读一遍 |
| **文件在搜索过程中被改动** | 块的 `readRange` 读到 EOF 就按实际长度处理；结果缓存用「读前 stat」作为新鲜度凭据，下次搜索 stat 一变即判过期。 | 无 |
| **取消（停止按钮）** | 复用池的 200ms abort 广播；worker 在块循环里检查 abort。已完成的块照常入装配表，但不会再有新块，收尾时按已到的块合并（与串行「截断」语义一致）。 | 无 |
| **命中上限** | 每块最多收 `maxMatchesPerFile` 条，合并时按块序截到同一上限并置 `truncated`。某块到达上限 ⇒ 整份文件必然超限，所以不会少报。 | 峰值回传 W × 上限 条命中 |

## 6. 性能瓶颈与取舍

先说测量（本机 20 核 / Windows，120MB 单行稀疏命中的日志，页缓存已热，8 个 worker）：

| 阶段 | 单块 4MB 耗时 | 说明 |
| --- | --- | --- |
| `putBytes`（JS → wasm 拷贝） | 0.22 ms（18 GB/s） | 可以忽略 |
| `find_all`（匹配） | 1.45 ms（2.8 GB/s） | ASCII 字面量走 memmem 类算法，很快 |
| `line_starts`（行起点表） | 5.6 ms（**0.7 GB/s**） | **隐形大头**，比匹配慢 4 倍 |
| `utf8_valid` | 0.3 ms（12 GB/s） | ASCII 快速路径 |

`line_starts` 之所以慢，不是因为扫字节慢，而是「每行 4 字节」的数组要跨 wasm 边界
拷贝出来（4MB 块 ≈ 800KB）。而分块搜索里**每块都要知道行数**（给后面的块算行号基准），
绝大多数块却一条命中都没有——为它们建整张表是纯浪费。

因此给内核加了 `line_count(ptr, len, upto)`：只返回 `[0, upto)` 内的行首个数，
8 字节一组用位运算筛选（`(x - 0x01..) & !x & 0x80..`），实测 **3.6 GB/s**（4.6ms → 1.1ms）。
现在只有**有命中的块**才建行起点表（建了才能算列号/预览）。

端到端效果：

| 场景 | 串行流式 | 并行分块 | 加速 |
| --- | --- | --- | --- |
| 120MB 文件，32 块一次性派给 8 worker | 361 ms | 76 ms | **4.75×** |
| 同上，走完整两段（主场发现 + 补块场） | 361 ms | 161 ms | 2.2× |
| 8MB 文件（9 块）走真实搜索链路（含池冷启动） | — | 144 ms | — |

两段式那行说明了一个真实的取舍：**发现「这是个超大文件」本身就要一轮往返**，这一轮
不可能并行（只有一个 worker 在 stat），而队列往往在这时就排空了，所以后续必须补一场。
想把 4.75× 变成稳定收益，就得让宿主提前知道体积——那要预扫全部文件（8 万次 stat，
秒级开销），对「只有少数大文件」的常见分布不值得。

其余瓶颈：

1. **结果回传的结构化克隆**：每条命中带一个预览字符串。命中密集的模式（如搜 `e`）在大文件上
   会成为主要开销，所以每块都有上限，合并后按上限截断。
2. **页缓存 vs 冷盘**：热缓存下加速比接近线性；冷盘 + 机械盘时并发读会 seek 抖动，
   加速比可能 < 1（见第 4 节建议）。
3. **长尾**：块数 < 4W 时收尾阶段只剩少数 worker 在跑。`balanceLimit` 就是为此留的余量；
   大文件上成本最优值给的块数通常远超 4W（1GB → 163 块），长尾由 √S 那一项控制。
4. **内存峰值**：`W × chunkSize` 而不是「文件大小」。默认参数下 16 线程 × 32MB = 512MB 上限，
   实际 100MB 文件只有 8 × 2MB。
5. **不做的事**：不给超大文件做结果缓存预热（第二次搜索靠结果缓存直接回放，仍是 O(命中数)
   的组装成本）；不为单文件保留专属 worker（会和普通文件抢队列，反而拖慢整体）。

## 7. 配置与适用场景

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `flySearch.chunkAboveMB` | 2 | 超过这个体积才**进入收益估算**；真正拆不拆由 `shouldChunk` 逐文件决定（一般 4MB 起才划算）。0 = 关闭（永远串行流式）。 |
| `flySearch.chunkMemoryMB` | 32 | 单 worker 缓冲预算，块大小受它约束。 |
| `flySearch.chunkCrowdMB` | 2 | 池子还剩大量字节要扫时，超过这个大小才仍并行分块（0 = 关闭闸门，32 = 保守）。 |
| `flySearch.diskType` | auto | 磁盘介质探测。机械盘上并发读会退化成随机寻道，探测到旋转介质就关掉分块（0.1.84）。 |
| `flySearch.parallelWorkers` | 0（自动） | 并发上限。机械盘建议 2~4。 |

适用：

- 单个 2MB ~ 数 GB 的文本文件（日志、CSV、dump），UTF-8/ASCII。2~8MB 这一档块数只有 1~4 块，
  并发度被块数卡住（`min(workers, 块数)`），收益主要来自「两份文件同时开跑」而不在单文件内部。
- 本地磁盘（`file://`），worker 能直接 `readSync` 自己的区间。
- 需要「快」而不是「省内存到极致」：内存上限是 W × 块，而不是文件大小。

不适用 / 自动退化：

- 非 UTF-8（UTF-16/GBK）、二进制、单行超长 → 串行流式。
- `chunkAboveMB = 0` 或 `parallelWorkers = -1` → 串行流式。
- 远程 / 虚拟文件系统（`vscode.workspace.fs` 才读得到）→ 串行路径（走宿主 `streamSearchFile`）。

## 9. 如何验证与调参

1. 输出面板（`flySearch.showLog`）里每次分块会打一行：
   `chunked <路径> size=… chunks=N`，以及 `hit/miss <路径> chunks=N items=M <ms>`。
2. 想对比串行/并行：把 `chunkAboveMB` 设成 0 再搜一次，比较同一份文件在 `done` 行上的耗时。
3. 想确认没有漏报：同一份文件分别用并行与串行搜一次，比对命中数（测试里就是这么锁的）。
4. 调参顺序：先看 `chunks=N` 是否 ≥ 4 × workers；再看内存是否吃紧（调小 `chunkMemoryMB`）；
   机械盘把 `parallelWorkers` 降到 2~4 再看。
