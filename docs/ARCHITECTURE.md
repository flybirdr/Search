# 文件处理架构规定

本文件是搜索插件的分层架构约定。所有新功能先回答「这属于哪一层」，再动手。

## 分层与职责

```
┌─────────────────────────────────────────────────────┐
│  表现层（Webview 前端）                              │
│  media/panel.js + src/ui/html.ts 生成的骨架          │
│  输入参数 · 展示结果 · 高亮 · 下发命令 · 交互        │
└───────────────▲───────────────────┬─────────────────┘
                │ postMessage        │ action/state
┌───────────────┴───────────────────▼─────────────────┐
│  宿主桥接层（TS 扩展宿主）                           │
│  src/ui/panel.ts · src/search/controller.ts         │
│  消息路由 · 文件字节搬运 · VS Code API · 状态持久化  │
└───────────────▲───────────────────┬─────────────────┘
                │ 内存协议(alloc/传入/传出) │
┌───────────────┴───────────────────▼─────────────────┐
│  内核层（Rust → WASM）                               │
│  rust-core/src/lib.rs + src/engine/wasm.ts 封装      │
│  正则编译 · 搜索 · 计数 · 替换 · 展开 · 分块扫描     │
└─────────────────────────────────────────────────────┘
```

### 表现层（TS 前端）

- 收集用户输入：查找文本、替换文本、模式（普通/扩展/正则）、选项（大小写、全字、dotAll…）、文件过滤器、搜索范围
- 展示搜索结果卡片、分组、折叠、状态行，负责结果高亮与定位跳转的触发
- 把用户动作封装成命令消息（`action`）下发给宿主；布局/条件状态（`state`/`layout`）上报
- **禁止**：任何匹配计算、任何文件读写、直接调用内核

### 宿主桥接层（TS 扩展宿主）

- 在前端与内核之间转发参数与结果，不做匹配计算
- **文件 I/O 的唯一出入口**：经 `vscode.workspace.fs` 列目录、stat、读字节、写回（这是唯一能覆盖远程/虚拟文件系统的通道）
- 衔接 VS Code：编辑器跳转与高亮（decorations）、命令面板、workspaceState/globalState 持久化
- 把文件字节送进 WASM 内存、把内核产物搬出来；对内核而言它只是「字节管道」

### 内核层（Rust）

- 只认「文本字节 + 参数」，不认 VS Code 类型（`Uri`、`TextDocument` 等一律不得进入内核）
- 负责**全部计算**：正则编译（fancy-regex）、`find_all` / `count` / `replace_all` / `expand_at`，以及目标架构下的流式分块扫描、编码判定、行号换算
- 落盘前的最终产物（替换后的完整文本或逐段 patch）由内核产出，宿主只负责 `write`

## 数据流（一次「全部」搜索）

1. 前端把 `{query, replace, mode, flags, filters, scope}` 打包成 `action: findInFiles`
2. 宿主 `controller.ts` 调 `SearchCore.compile()` 编译正则（Rust）
3. 宿主逐文件 `vscode.workspace.fs` 取字节（大文件走流式分块），喂给内核 `find_all`
4. 内核返回匹配数组（UTF-16 偏移由 wasm.ts 映射回 TS 侧）
5. 宿主组装结果记录，推送回前端渲染；用户点击结果时由宿主执行跳转 + 高亮

## 边界规则

1. **计算永远在内核**：新增任何匹配/替换/统计逻辑，一律写进 Rust，TS 侧不出现手写循环匹配的代码
2. **I/O 永远在宿主**：WASM 没有文件系统能力，内核不得假设自己能打开文件；所有路径→字节的转换由宿主完成（除非将来整体迁移到 WASI，见下）
3. **前端零 I/O、零计算**：前端拿到的永远是组装好的记录对象
4. **内核协议保持纯函数风格**：`alloc` → 写入 → 调用 → 读结果 → `dealloc`，无回调、无环境依赖，保证内核可以脱离 VS Code 单测（现状：`test/engine.test.mjs` 直接跑 WASM）

## 现状差距与迁移路线

| 阶段 | 内容 | 状态 |
|---|---|---|
| P1 | 正则编译、搜索、替换、展开全部在 Rust 内核 | ✅ 已完成 |
| P2 | 流式分块扫描下沉：换行切分、行号基线、贴块尾判定移入 Rust，宿主只负责按块喂字节 | 现在切分逻辑在 `src/search/stream.ts`（TS） |
| P3 | 替换落盘内核化：内核产出替换后全文或 patch 序列，宿主只调 `writeFile` | 现在替换结果由内核产出、宿主组装写回 |
| P4（可选） | WASI 化（`@vscode/wasm-wasi-core`）：内核拿到预开句柄自己 read/write，本地文件真正「Rust 执行文件操作」；代价是远程/虚拟 FS 仍需宿主中转，且引入异步运行时改造 | 未启动 |

P2/P3/P4 属于增强，不阻塞功能迭代；做与不做以「性能或正确性是否遇到瓶颈」为准。
